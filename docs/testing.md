# 検証方法

Rustテスト、静的検査、Linuxのsystemdを使った隔離試験をCIで実行します。結果はコミットごとのCIと配布成果物で確認します。過去の結果をソースディレクトリへ蓄積しません。

```sh
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
python3 -m unittest discover -s tests -p 'test_distribution.py' -v
cargo build --release --locked --bins --examples
sudo python3 tests/linux_acceptance.py target/release/bdsctl target/release/examples/fake_bds
```

隔離試験は一時ユーザー・一時サービス・模擬BDS・一時ワールド・ループバックの空きポートを使います。実際のMinecraftサービスを停止・変更しません。起動確認、停止バックアップ、コピー失敗からの復帰、コピー親プロセス終了時のロック保持、復元、更新失敗時のワールドと本体の巻き戻し、中断後の復旧、root操作結果の読み取り、同じ操作の再実行拒否を検証します。

常駐するRustの2プロセスについて合計PSSと待機時CPUを30秒測定します。この間に状態ファイルも確認コマンドの記録も変化せず、監督の自発的な定期起床がないことも確認します。状態記録が15秒以上古くても、実行状態の照合でstatusが成功することを検証します。ログ出力を閉じた子プロセスを終了させ、終了通知だけで監督が起き、systemdが再起動することも確認します。BDS本体・Caddy・実際のDiscordへの通知送信はこの測定に含めません。本番切り替え時には、実際のワールド・Minecraftクライアント・Discordでの通知と操作も確認してください。

配布テストでは、ソースがない配布先での検証、バイナリ改変の拒否、異なるコミットの拒否、チェックサム不足の拒否、未コミットのソースからの包装拒否を確認します。配布物の`validation.json`に、そのコミットのLinux実測結果を含めます。

異常時の終了待ちは1MiBの終了ログを出す模擬BDSで確認します。HTTPは署名付きPING、曖昧な本文長の拒否、不完全なヘッダー・本文の絶対期限、遅い要求と通常要求の並行処理、接続上限を検証します。初回取り込みは確定途中の失敗からの再実行と、データ配置前・版切り替え後の中断からの復旧を確認します。

定期更新の試験は`fake_bds`と同じディレクトリの`auto_update`試験用実行ファイルを使用します。外部のバージョン情報だけを模擬し、実際のメンテナンス処理で、変更なし・取得元の障害時の無停止、新版の即時適用、失敗時の切り戻しと再試行拒否、古い版へのダウングレード拒否、他の処理との排他、手動停止の維持、日次バックアップとの分離を検証します。試験用実行ファイルは配布物へ含めません。

運用試験では、保守状態を別プロセスから読み直しても予約処理・明示的な再起動・systemd起動が抑止され、終了時に元の稼働状態を復元することを確認します。容量不足の事前検査では予告・停止・トランザクション作成が発生しないことも確認します。復元用アーカイブは独立した保存先と一時サービスへ取り込み、同じ版の本体とワールドが起動できること、既存データへの上書き、改変、リンクを拒否することを検証します。

配布処理は一時的な模擬設置先で、停止前検証の無変更、途中失敗時のバイナリ・サービス定義・ビルド情報の復旧、停止済みサービスの維持、設置失敗時の保守維持、有効化設定の維持を検証します。本番VPSの設置先では試験しません。

異常終了したBDSと`reset-failed`後の状態では、日次・手動バックアップが拒否され、既存の正常世代と最終成功記録が変わらないことを実際のsystemdで確認します。起動前処理を旧制限時間より長く遅延させた上で、中断した更新の復旧とBDS起動が成功することも確認し、起動確認そのものの期限は既存の応答不能・待受なし試験で確認します。容量見積もりはファイルの作成・削除と並行させ、旧データ取り込みは公式ファイルとパック全体の削除を検出して配置を確定しないことを検証します。

稼働中に手動復旧と起動前専用コマンドを実行し、版のリンク・起動ID・コンソール記録が変わらないことを確認します。新規初期化はデータ公開後の失敗から、版の取得元が不通でも同じ確定記録で再開し、データ公開前・版の有効化後の中断も復旧します。確定記録のない既存データは採用も削除もしないことを確認します。

操作記録は既存JSONの読み書き互換と未知の段階・操作種別の拒否を確認します。Discord受付記録の破損時は再要求でも記録を上書きしません。既定設定の表示は設定ファイルなしで実行し、設定例の省略項目が同じ既定値を継承することを検証します。
