# 異常時の確認

- `sudo bdsctl status`：Minecraftの状態・版、保守状態、処理の実行状態、最後のバックアップ作成・復帰成功、更新候補、次回予定、空き容量を要求時だけ取得します。終了コード0は情報取得の成功を示し、稼働中・接続可能の保証ではありません。
- `sudo bdsctl status-json`：今回の起動ID、BDSのPID、起動・異常・正常終了の生の記録。`changed_at`は最後の状態変更時刻です。
- `sudo bdsctl inventory`：バックアップの保存理由・日本時間・論理サイズ・保護状態と、障害調査用データのサイズ。共有ファイルのある世代の論理サイズは、実際のディスク使用量とは異なります。
- `systemctl status bds.service`と`journalctl -u bds.service`：起動回数上限、停止待ち、起動前の復旧エラー。
- `/var/lib/bds-supervisor/*.json`：最新20件の異常理由と直近のBDS標準出力。
- `/var/lib/bds/state/transaction.json`：中断した更新・復元の段階と復旧元。
- `/var/lib/bds/state/discord-outcome.json`：最後にroot側で受けたDiscord操作のIDと結果。

## プロセスは稼働中だが接続できない

起動後の定期的な正常性確認は行いません。接続経路・Minecraftのログ・クライアントのバージョンなどを確認し、必要なら`sudo bdsctl restart`またはDiscordの`/restart`で正常停止・再起動を要求します。

## 停止が終わらない

停止が完了するまでバックアップや二重起動を行いません。`stop`への反応、BDSのプロセス状態、ディスクI/O、空き容量を調べてください。管理者が強制終了を選ぶ場合、ワールドの保存が完了しているとは扱えません。正常終了記録がない状態で作られたコピーを正常バックアップと呼ばないでください。

## 初回取り込みが中断した

`/var/lib/bds/state/import.json`がある場合、初回取り込みの確定処理が残っています。BDSを停止し、ディスク容量・所有者変更・BDS本体の配置などの失敗原因を直してから、`sudo bdsctl recover`を実行します。同じ`import-legacy`の再実行でも、コピー済みのデータから確定処理を再開します。移行元を再コピーしたり、既存ワールドを削除したりしません。

コピー途中で終了して記録がまだない場合は、停止中に`recover`で作業用ディレクトリを整理し、元の`import-legacy`を再実行します。記録や配置が矛盾する場合は自動処理を止めます。`import.json`や配置済みデータの削除で回避しないでください。取り込みの確定までは通常の起動・更新・復元を行いません。

## 更新・復元が中断した

BDSの停止を確認してから`sudo bdsctl recover`を実行します。起動前にも復旧処理が走ります。記録やバックアップが壊れていれば、無理に起動せず停止します。`transaction.json`の削除だけで復旧したことにはなりません。

更新版の起動失敗で巻き戻した場合は、その版を`rejected-release.json`に記録します。自動では同じ版を適用しません。原因を直して明示的に再試行するときは`sudo bdsctl update`を実行します。

## Discord操作が「結果不明」で次の操作を受け付けない

受付したIDは`/var/lib/bds-discord/job.json`、実行結果は`/var/lib/bds/state/discord-outcome.json`です。結果不明の操作を再送しない設計なので、サービス終了と受付側の再起動が重なると、管理者の確認が必要になる場合があります。

Minecraft・OSの実際の状態と、`bds-discord-restart.service`・`bds-discord-reboot.service`の稼働状態を調べてください。OS再起動の場合は記録の`boot`と`/proc/sys/kernel/random/boot_id`が異なれば再起動済みです。処理が残っていないことを確認した後、受付サービスを停止し、`job.json`を管理者用の退避先へ移して受付サービスを起動すると、新しい確認を受け付けられます。実行中の記録を消したり、同じ確認を再送したりしないでください。

OS再起動要求が受理された後は`reboot-pending.json`に起動IDを残し、同じOS起動中の別操作を拒否します。OS起動IDが変われば自動で解除します。OS再起動が実際には進んでいない場合は、systemdのジョブとBDS停止を調べた上で、この記録を退避してからBDSを起動してください。

## ワールド・アドオンの保守

```sh
sudo bdsctl maintenance-begin
# 正常終了を確認してから /var/lib/bds/data を編集
sudo bdsctl maintenance-end
```

保守開始はゲーム内予告・正常停止を行い、保守状態をディスクへ保存します。処理が失敗したら編集を始めず、原因を解決して同じコマンドを再実行します。予約バックアップ・更新は保守中の回をスキップし、Discordには保守中と返します。実行直前にもroot側で拒否するため、保守開始前の確認ボタンも起動につながりません。

VPSが再起動しても保守状態は解除されません。BDSサービスの起動条件で停止を維持します。`recover`と`restore`は停止したまま使用できます。終了時は設定と配置を確認して所有者を整え、保守開始前に稼働していた場合だけ起動します。失敗した場合は保守状態を維持します。ワールド編集中に状態ファイルを削除して解除しないでください。

## 必要時の手動書き出しと新規環境への復元

```sh
sudo bdsctl snapshots
sudo bdsctl export BACKUP_ID /var/backups/bds-recovery.tar.zst
```

アーカイブには同じ版のMinecraft本体、ワールド・設定・独自パック、スナップショット情報、公開管理設定、ファイルごとのSHA-256一覧が入ります。公式配布の継続に依存せず復元できます。生成物は所有者だけが読める権限です。ワールドや設定には個人情報を含む可能性があるため、公開場所へ置かないでください。チェックサムは破損検知であり、第三者から来たアーカイブの正当性を保証する署名ではありません。

通常のバックアップはVPS内で保存・管理し、外部保存先への転送は行いません。`export`は必要時の手動操作です。書き出したファイルは`zstd -t`で圧縮データを確認できます。

新規VPSには、検証済みのbdsctl配布物と必要なシステムソフトウェアを設置し、復元先用の`/etc/bds/config.toml`を用意します。自動起動・タイマーはまだ有効にしません。アーカイブの管理設定は参考用で、復元先のパスやDiscord設定を自動上書きしません。Webhook、Caddy、通信許可設定は別に保管・復元します。

```sh
sudo bdsctl import-package /var/backups/bds-recovery.tar.zst
sudo systemctl start bds.service
sudo bdsctl status
```

取り込みは新規の保存先専用です。既存ワールドや現在のBDS版がある場合は拒否し、リンク・特殊ファイル・重複項目・チェックサム不一致も拒否します。配置後にサービスやタイマーを自動起動しません。取り込み確定が中断した場合は、旧データ取り込みと同じく停止状態の`recover`で再開します。展開途中の残骸も、停止中の`recover`で整理できます。

アプリから接続し、ワールド・アドオン・権限を確認した後、バックアップの停止・起動を一巡させます。確認が終わったらDiscord受付と日次・更新タイマーを有効にします。管理ツールの採用版はGitHub Releaseから取得できるようにしてください。

## 保存世代の整理

`retention`は毎朝の保存回数、`extra_retention`は手動・更新前を合わせた保存回数です。既定値はそれぞれ14です。保存理由のない以前の形式は手動として扱います。保護済みはどちらの枠にも含めず、自動削除しません。保護解除後は次の正常なバックアップ処理で整理対象になります。

障害調査用データと保護済み世代は`inventory`で確認し、必要なデータかどうかを判断してから整理します。障害調査用データを削除する際は、対応する中断処理が解決済みであることを先に確認します。バックアップの一部のファイルを直接削除・編集しないでください。
