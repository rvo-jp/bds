# 設計

## 常駐処理

`supervise`はBDSの直接の親プロセスです。標準入力のパイプへコマンドを書き、標準出力を直接読み取ります。FIFO、screen、tmux、journalctlでのログ追尾は使いません。起動確認が終わったら、ログ・コンソール操作・停止要求・子プロセス終了のイベントを期限なしのpollで待ちます。LinuxのsignalfdでSIGTERM・SIGINT・SIGCHLDをI/Oと一緒に受け取り、子の終了確認用のスレッドや定期ポーリングは追加しません。シグナルは通知スレッドの作成前に遮断し、BDSの起動直前には元の遮断設定へ戻します。起動中だけ接続受付とコンソール応答の確認期限を持ちます。systemdの`TimeoutStartSec`は無制限とし、起動前の中断復旧とBDS本体の起動確認の期限を分離します。監督内の起動確認期限はBDS子プロセスの作成後から計測し、管理コマンドの再試行待ちも起動前復旧の完了後から計測します。

状態ファイルは起動・起動完了・停止開始・終了・異常時にだけ更新し、changed_atは最後の状態変更時刻です。稼働判定は今回のOS起動ID・systemdの起動ID・サービス状態と起動完了記録を照合し、記録の古さでは失敗と判定しません。コンソールの入力待ちと通知キューには上限を設けます。BDSを強制終了して新しいBDSを起動する復旧は行いません。

監督の正常終了記録は、systemdのInvocation IDとBDSの終了コードに結び付けます。管理プロセスの終了コードだけでは保存完了を判定しません。systemdが正常停止中に監督へSIGTERMを送る場合も、BDSの終了コード0を記録してから終了します。状態記録などのエラーで通常の監督を続けられない場合も、古いコンソール送信待ちを捨ててstopを送り、BDSの標準出力を読み捨てながら終了を待ちます。停止の応答がない間は二重起動やコピーを避け、管理者が調査できる状態を残します。

`discord`はループバックでHTTPを受け、Ed25519署名と±5分のタイムスタンプを検証します。署名検証前の本文サイズは64KiBまでです。受付は接続から読み取り完了までの絶対期限2秒、ヘッダー8KiB、本文64KiB、同時4接続を上限とします。Content-Length付きのHTTP/1.xを1接続1要求で受け、chunked・重複したContent-Length・Expectは拒否します。HTTPヘッダーの解析はhttparseを使います。要求本文の読み取りは並列ですが、確認・受付記録の変更は排他します。Caddy側でも本文サイズと通信時間を制限します。受付ユーザーにワールド・バックアップ・OS管理の包括的な権限を渡しません。Polkitは固定サービス2つのstartだけを許可します。

## 操作の途中で終了した場合

変更前のBDS版、バックアップID、操作段階、実行者PID・起動時刻、OS起動IDを、ファイルの同期と原子的置換で記録します。版やデータを変える前に記録を書きます。起動前の`recover`が中断を見つけた場合は、バックアップを独立コピーして変更前の版へ戻します。PID番号の一致だけで処理中とは判断しません。手動復旧と起動前復旧は入口を分け、前者はサービスと全プロセスの停止、後者はactivating・MainPID=0・自分がControlPIDでありサービス内に他プロセスがいないことを確認してから、共通の復旧処理へ進みます。

バックアップからの復元中に旧データの退避だけが終わった場合も、次回の復旧は同じバックアップから再作成できます。バックアップの破損や記録の不正がある場合は自動起動を止めます。復旧処理は元のバックアップを編集しません。

起動を伴う処理は、メンテナンスロックと、その処理の生存情報を持つ起動許可記録を使います。バックアップの停止期間中に別の起動が入り、コピー中のワールドが動き出すことを防ぎます。定期更新は公式の版を確認する処理だけを差し替えられる構造にし、テストでは外部の配布元へ接続せず、本番と同じ停止・バックアップ・適用・復旧処理を検証します。定期更新と日次バックアップは同じロックで排他し、定期更新はロック取得後に公式の版と現在の版を比較します。変更なし・失敗済みの版・古い版では停止しません。日次バックアップは更新候補の適用を行いません。

日常の操作は`bdsctl`に統一し、複数の管理者がsystemctlで直接同時操作しないでください。

データはBDSユーザー所有、本体とバックアップはroot所有です。rootのメンテナンス処理だけが本体リンクを変更します。公式パックは本体側、独自パックはデータ側へ置き、同名の衝突を拒否します。公式パックを直接編集している環境は、独自パックへ分離してから移行します。

## 採用しない機能

常駐Python・シェルの監督チェーン、常時接続Discord Gateway、BDS稼働中のバックアップ、自動の強制終了、毎日の全量gzip圧縮、古い互換コマンド、Web管理画面は持ちません。BDSの管理と無関係な外部サイトへの自動投稿は含めません。

## 管理者の保守と災害復元

保守モードはroot所有の永続記録で、共通操作ロックの下で開始・終了します。終了時は開始前の稼働状態を復元し、失敗時は保守を残します。systemdの起動条件と起動直前の確認で、保守中の自動起動を防ぎます。Discord受付時の案内に加えroot操作時にも拒否し、予約処理は正常スキップします。状態表示と容量一覧は要求時だけ取得します。

スナップショットはdaily/manual/update/safetyの理由を記録し、日次と臨時を別枠で保持します。復元直前のsafetyは保護します。停止済みデータからの通常バックアップは、inactiveと同じOS起動中の正常終了記録を必要とし、異常停止時のデータで通常世代を置き換えません。停止前に容量・候補本体の存在を確認し、稼働中の容量見積もりだけは消失したファイルを許容します。停止後の容量確認・コピー・検証は厳密に行います。外部保存先への転送は行いません。必要時の手動書き出しには稼働データへのリンクを含めず、公式本体の実ファイルとデータ、公開管理設定、全ファイルのハッシュを収録します。新規領域への取り込みは検証後に公開し、確定処理は永続した取り込み記録で再開します。秘密情報やプロキシ設定は別管理です。

管理ツール自身の通常更新は開発PCから開始し、停止前検証・保守・設置・元の稼働状態の復元を順に行います。設置の通常エラーは変更前ファイルを戻し、電源断などで復旧できない状態は保守状態と配布記録を使って検証済み配布物を再設置します。成功後の旧ファイルは保持せず、採用版はGitHub Releaseに保管します。

初期化・旧データ移行・アーカイブ取り込みは、準備用ディレクトリと`import.json`による共通の初回配置処理を使います。確定記録が公開される可能性が生じるまではディレクトリのガードが後片付けを担当し、その後は確定記録が再開に必要なデータを保持します。通常データ領域の作成・所有者の設定・版の有効化を途中で中断しても、同じ記録から再開します。

## コードと定義の所在

`operations/mod.rs` は操作の公開窓口です。実装は `lifecycle.rs`（起動停止）、`maintenance.rs`（バックアップと更新）、`placement.rs`（初期配置の確定とデータ移行）、`legacy.rs`（停止前の旧公式パック検証）、`restore.rs`（復元と巻き戻し）、`recovery.rs`（中断復旧）、`state.rs`（操作状態と共通条件）に分けます。同じ操作の別実装は持ちません。

永続記録は担当モジュールの `Record<T>` 定数でファイル名・データ型・権限を定義します。保存と削除の同期処理は `src/state.rs`、排他ロックの配置も同じモジュールに集約します。処理段階・保存理由・Discord操作は列挙型で表し、Rustの値・保存名・表示名・文字列からの変換は一つの対応表から作ります。不明な段階を正常な状態として扱いません。操作記録と起動許可は同じプロセス識別・生存判定を使います。既存のJSONの名前と構造は維持します。

Discordの受付・登録・実行・サービス生成・Polkit権限は同じ操作一覧を参照します。受付済み記録が壊れている場合は、新しい要求で上書きせず管理者の確認を求めます。

設定の既定値は `Config::default()` を正本とし、設定例は必要な上書きだけを記載します。全既定値は `--default-config` でコードから出力します。READMEは運用の説明、設計文書は責務と制約の説明に使い、別の実装や過去版は置きません。

旧構成の上書き更新で残った公式ファイルは、移行時に現行版と混在させません。停止前の検証で、参照する旧公式版の同じパスとハッシュが一致するファイルだけを移行準備記録に含めます。現行ファイルの欠落・改変は許可せず、取り込み時もファイル一覧とハッシュを再検証します。確認後の変更・未確認の追加は拒否します。公式パックの照合処理は、例外なしの厳密比較と移行準備記録による比較で同じ実装を使います。元データは変更せず、記録は初回配置の確定時に消します。
