# 設計

## 常駐処理

`supervise`はBDSの直接の親プロセスです。標準入力のパイプへコマンドを書き、標準出力を直接読み取ります。FIFO、screen、tmux、journalctlでのログ追尾は使いません。コンソールの入力待ちと通知キューには上限を設けます。BDSを強制終了して新しいBDSを起動する復旧は行いません。

監督の正常終了記録は、systemdのInvocation IDとBDSの終了コードに結び付けます。管理プロセスの終了コードだけでは保存完了を判定しません。systemdが正常停止中に監督へSIGTERMを送る場合も、BDSの終了コード0を記録してから終了します。停止の応答がない間は二重起動やコピーを避け、管理者が調査できる状態を残します。

`discord`はループバックでHTTPを受け、Ed25519署名と±5分のタイムスタンプを検証します。署名検証前の本文サイズは64KiBまでです。Caddy側でも本文サイズと通信時間を制限します。受付ユーザーにワールド・バックアップ・OS管理の包括的な権限を渡しません。Polkitは固定サービス2つのstartだけを許可します。

## 操作の途中で終了した場合

変更前のBDS版、バックアップID、操作段階、実行者PID・起動時刻、OS起動IDを、ファイルの同期と原子的置換で記録します。版やデータを変える前に記録を書きます。起動前の`recover`が中断を見つけた場合は、バックアップを独立コピーして変更前の版へ戻します。PID番号の一致だけで処理中とは判断しません。

バックアップからの復元中に旧データの退避だけが終わった場合も、次回の復旧は同じバックアップから再作成できます。バックアップの破損や記録の不正がある場合は自動起動を止めます。復旧処理は元のバックアップを編集しません。

起動を伴う処理は、メンテナンスロックと、その処理の生存情報を持つ起動許可記録を使います。バックアップの停止期間中に別の起動が入り、コピー中のワールドが動き出すことを防ぎます。日常の操作は`bdsctl`に統一し、複数の管理者がsystemctlで直接同時操作しないでください。

データはBDSユーザー所有、本体とバックアップはroot所有です。rootのメンテナンス処理だけが本体リンクを変更します。公式パックは本体側、独自パックはデータ側へ置き、同名の衝突を拒否します。公式パックを直接編集している環境は、独自パックへ分離してから移行します。

## 採用しない機能

常駐Python・シェルの監督チェーン、常時接続Discord Gateway、BDS稼働中のバックアップ、自動の強制終了、毎日の全量gzip圧縮、古い互換コマンド、Web管理画面は持ちません。Game8投稿など、BDS管理と別目的の処理は外部の独立サービスとして扱います。既存の独立した投稿タイマーを移行作業で削除しないでください。
